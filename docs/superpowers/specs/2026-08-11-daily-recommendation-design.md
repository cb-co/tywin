# Daily recommendation on the overview

## Context

The overview page shows what is true — net worth, month-to-date income and
spending, budget usage, what is due soon — and says nothing about what any of it
means. This adds one card that does: a short piece of coaching, generated by
Gemini from a redacted snapshot of the user's own numbers, refreshed at most
twice a day.

The card sits between the stat grid and the Upcoming rail, so the hard figures
are read first and the commentary follows them.

Free-form coaching, deliberately: the model decides whether today is worth a
warning, a nudge, or praise, rather than being pinned to one template. The
guardrails are on what it may claim, not on what it may talk about.

## What this is not

- Not investment, tax, or product advice. The prompt forbids it.
- Not a chat surface. One card, no input, no follow-up.
- Not a history. Only the current recommendation is stored.

## Storage

One table, one row per user, upserted:

```sql
create table public.daily_recommendations (
  user_id      uuid primary key references auth.users (id) on delete cascade,
  headline     text not null,
  body         text not null,
  tone         text not null check (tone in ('good', 'watch', 'neutral')),
  locale       text not null,
  generated_at timestamptz not null default now()
);
```

`user_id` is the primary key rather than a surrogate id with a unique index,
because a second row for the same user has no meaning here. Nothing reads
yesterday's recommendation, so there is no history table and no `created_at`
distinct from `generated_at`.

RLS mirrors `savings_goals` exactly — owner-only select/insert/update/delete
against `(select auth.uid()) = user_id`. No delete policy is strictly needed by
the app, but omitting one from the set is the kind of asymmetry that later reads
as an oversight.

Migration: `supabase/migrations/<ts>_daily_recommendations.sql`, followed by
`npm run db:types`.

## Freshness

```ts
// lib/overview/recommendation/freshness.ts
export const RECOMMENDATION_TTL_MS = 12 * 60 * 60 * 1000;

export function isStale(
  generatedAt: string,
  rowLocale: string,
  locale: string,
  now = new Date(),
): boolean;
```

Stale means **either** older than 12 hours **or** generated in a different
locale than the one being rendered. The locale clause is what stops a user who
switches to Spanish from reading English advice for the rest of the half-day
window; without it the cache is correct about time and wrong about language.

Pure and separate from any query so it can be tested across the boundary
without a database.

## The snapshot

`lib/overview/recommendation/snapshot.ts` exports the queries and a pure
`buildSnapshot(rows)` that shapes them. The split exists because the redaction
rules are the part most worth testing, and testing them should not require a
Supabase client.

The payload, with every amount rounded to whole currency units — false
precision costs tokens and buys nothing at this altitude:

```ts
type RecommendationSnapshot = {
  asOf: string;              // "2026-08-11"
  dayOfMonth: number;
  daysLeftInMonth: number;
  baseCurrency: string;
  netWorth: number;
  monthIncome: number;
  monthExpense: number;
  monthlySubscriptions: number;
  budgets: { category: string; budget: number; used: number }[];
  accounts: { type: string; currency: string; balance: number }[];
  loans: { currency: string; outstanding: number; installment: number }[];
  goals: { target: number; saved: number; targetDate: string | null }[];
  upcoming: { kind: string; amount: number; currency: string; dueInDays: number }[];
};
```

Most of this already exists. `getOverview()` in `lib/overview/queries.ts`
computes net worth, cashflow, budget totals, monthly subscription cost and the
upcoming rail; `getBudgetOverview()` gives per-category budget and usage;
`getGoalsOverview()` gives goal progress. The snapshot reuses those rather than
issuing a parallel set of queries, and strips what they carry that must not
leave the server.

### Redaction

Never included, enforced in `buildSnapshot` rather than by convention:

| Excluded | Why |
|---|---|
| `display_name`, email, user id | Identifies the person |
| Account names, institutions, last 4 | Identifies the bank and the card |
| Goal names | Free text the user wrote; can be anything |
| Subscription names | Names services the person pays for |
| Transaction descriptions, merchants | The most sensitive text in the app |

`upcoming` therefore carries `kind` (`card_payment`, `loan_installment`,
`subscription`) in place of the human title `getOverview()` builds, and
`accounts` carries type and currency in place of the name.

Category names are the one piece of user-authored text that survives. That is a
deliberate trade: "Dining is running hot" is the difference between coaching and
a horoscope, and category names are chosen from a small, generic vocabulary in
practice.

A test serialises a snapshot built from fixture rows containing every excluded
field and asserts none of them appear in the JSON. This is what stops a column
added to `getOverview()` later from quietly riding along into a prompt.

## Inference

`lib/overview/recommendation/llm.ts`, modelled directly on
`lib/subscriptions/llm/brand.ts`:

```ts
export const RecommendationSchema = z.object({
  headline: z.string().describe("A 3-6 word headline..."),
  body: z.string().describe("One or two sentences..."),
  tone: z.enum(["good", "watch", "neutral"]),
});

export async function inferRecommendation(
  snapshot: RecommendationSnapshot,
  locale: string,
): Promise<Recommendation | null>;
```

Same provider and call shape as the rest of the app: Gemini through the AI SDK
with a schema-constrained response, `abortSignal: inferenceSignal(...)`, and a
`catch` that returns `null`. Never throws — a missing recommendation is a
missing nicety, not an error anyone needs to see.

Budget: `DEFERRED_INFERENCE_BUDGET_MS` (90s). Nothing is blocked on this call.
The page has already rendered by the time it starts, so a cold call — 9 to 70
seconds per the notes in `lib/llm/budget.ts` — costs a card that fills in late
rather than a spinner anyone waits behind. A blocking budget here would lose the
answer on exactly the calls that matter most.

### Prompt

The system prompt establishes:

- Write in the user's language. The locale is **passed in**, never inferred from
  the data.
- Pick the single most notable thing in the snapshot. Do not survey everything.
- `headline`: 3–6 words. `body`: one or two sentences.
- Use only the numbers given. Never invent, extrapolate, or state a figure that
  is not in the snapshot.
- No investment, tax, or legal advice. No named products or services.
- Observe without scolding. Praise when the numbers deserve it.
- `tone` must match what the body says: `watch` when flagging a risk, `good`
  when the news is good, `neutral` otherwise.

## Reading and refreshing

`lib/overview/recommendation/queries.ts`:

```ts
export async function getRecommendation(
  locale: string,
): Promise<{ rec: Recommendation | null; stale: boolean }>;
```

Returns the cached row whatever its age, plus whether it needs regenerating.
That is what makes stale-while-revalidate possible: the card shows the previous
recommendation immediately and swaps in the new one when it lands, so the only
blank card anyone sees is on their very first visit.

`app/(app)/actions.ts` (new file — the overview route has no actions today):

```ts
export async function refreshRecommendation(): Promise<{ refreshed: boolean }>;
```

1. Require a user; return `{ refreshed: false }` if absent.
2. Re-read the row and re-check `isStale`. A second tab that raced this one has
   already written a fresh row, and the cheapest place to notice is before the
   inference call.
3. Build the snapshot. If the user has no accounts, return early — the overview
   renders its empty state in that case and never mounts the card anyway.
4. `inferRecommendation`. On `null`, return `{ refreshed: false }`; nothing is
   written, and the next page view tries again.
5. Upsert the row, `revalidatePath("/")`, return `{ refreshed: true }`.

Every failure path is silent and returns `refreshed: false`, matching
`resolveSubscriptionBrand` in `app/(app)/subscriptions/actions.ts`.

## The card

`components/overview/recommendation-card.tsx`, a client component rendered from
the server page between the stat grid and the Upcoming rail:

```tsx
<RecommendationCard rec={rec} stale={stale} />
```

On mount, if `stale`, it fires the action the way
`components/subscriptions/subscription-form-dialog.tsx:183` already does:

```tsx
void refreshRecommendation().then(({ refreshed }) => {
  if (refreshed) router.refresh();
});
```

`void` rather than `await` for the same reason it is load-bearing there — this
must never join anything's critical path.

A ref guards the effect so React's dev-mode double-invocation does not fire two
generations. Combined with the freshness re-check inside the action, the worst
case across tabs is one wasted call. That is not worth a lock.

Three render states:

| State | Renders |
|---|---|
| `rec` present | `ColorTile` + headline + body |
| `rec` null, refreshing | Skeleton at the card's settled height |
| `rec` null, not refreshing | `null` — no card, no error, no retry |

Tone maps to tokens that already exist in `app/globals.css`:

| `tone` | Tile colour |
|---|---|
| `good` | `var(--success)` |
| `watch` | `var(--warning)` |
| `neutral` | `var(--brand)` |

The card follows the page's existing language — `Card`, `ColorTile` at `md`,
`rise` with the next `--i` in the sequence, and the Upcoming rail's `--i`
increments to make room.

## i18n

Two strings under `Overview` in `messages/en.json` and `messages/es.json`: the
card's section label and the skeleton's aria-label. The recommendation text
itself is generated in the user's locale and is never run through next-intl.
